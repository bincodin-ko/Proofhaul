# 보고서 양식 — `docs/stack-recommendation.md`

이 양식을 그대로 쓴다. 섹션을 빼지 않는다. 숫자마다 출처(URL·확인 날짜)가 없으면 "미검증"이라고 표시한다.

## 편의성 채점 기준 (레이어별 비교표의 "편의성" 열)

5항목, 각 0~2점, 합계 10점. 점수보다 **월 운영 시간 추정치**가 더 중요하다 — 점수는 정성, 시간은 비용 계산에 들어간다.

| 항목 | 0점 | 1점 | 2점 |
|---|---|---|---|
| 배포 마찰 | 수동 SSH·스크립트 | 설정 후 git push | 처음부터 git push |
| 월 운영 시간 | 5시간 초과 | 2~5시간 | 2시간 미만 |
| 한밤중 장애 | 내가 깨야 한다 | 자동 재시작, 아침에 확인 | 제공자가 처리 |
| 로컬 개발 동일성 | 프로덕션과 다른 런타임 | 대부분 같음 | Docker/동일 런타임 |
| 탈출 비용 | 독자 API·데이터 형식 | 표준이지만 이전 작업 필요 | 표준(Postgres, S3 호환, Docker) |

월 운영 시간 기본 추정(사례에 맞게 조정):
- 관리형 플랫폼 조합: 0.5~1시간
- VPS + Coolify: 2~4시간 (백업 확인, 패치, 디스크, 가끔 재시작)
- VPS 수동 운영: 4~8시간
- 처음 세팅 시간은 별도로 적고 12개월로 나눠 월에 더한다

## 1. 워크로드 프로필
(Phase 0에서 확인받은 카드를 그대로)

## 2. 비용이 새는 지점
이 서비스에서 청구서를 좌우할 항목 1~2개와 이유. 항목은 내용으로 부른다(예: "파일 다운로드 과금"), 내부 번호로 부르지 않는다.

## 3. 항목별 비중 (고객 100명 시점 월 현금)

| 항목 | 월 비용 | 비중 |
|---|---:|---:|

인프라(호스팅+DB+스토리지) 합계가 전체의 30% 미만이면, 그 사실과 진짜 1위 항목을 **추천의 첫 문장으로** 올린다.

## 4. 레이어별 비교
레이어마다 표 하나. 후보 2~3개.

| 후보 | 출시 직후 | 고객 100명 | 고객 1,000명 | 월 운영 시간 | 편의성(/10) | 상한 설정 | 한국 리전 | 비고·함정 | 출처 |

## 5. 추천 스택 (주)

**월 총액 (현금 + 시간)**
| 시점 | 현금 | 운영 시간 | 시간 비용 | 합계 | $200 상한 대비 |
| 출시 직후 | | | | | |
| 고객 100명 | | | | | |

**이 추천이 틀리는 조건** — 3개 이내, 각각 숫자로. 예: "월 다운로드 5TB 초과", "동시 접속 500 이상의 실시간 기능 추가", "미국 사용자 비율 50% 초과"

**가장 큰 비용 함정과 방어책** — 하나. 상한 설정·알림·캐싱 중 구체적 조치.

## 6. 대안 스택
주 스택과 철학이 다른 것 하나. 같은 표 구조. "주 스택 대신 이걸 고를 사람은 누구인가" 한 줄.

## 7. 갈아타기 경로
규모가 커졌을 때 어느 층을 어디로 옮기는가. 데이터 층(DB·스토리지·인증)의 이전 난이도를 각각 표시.

## 8. 사지 말아야 할 것
지금 규모에서 돈 낭비인 것과 이유. 예: 유료 APM, 전용 DB 인스턴스, 멀티리전, 유료 CI.

## 9. 첫 주에 할 일
5개 이내, 순서대로. 첫 항목은 보통 "지출 상한·알림 설정".

## 10. 미검증 항목
검색으로 확인 못 한 숫자와 그 이유. 계약 전 사용자가 확인할 것.
