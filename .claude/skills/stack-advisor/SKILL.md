# 인프라 스택 추천

## 이 스킬의 목적

"제일 유명한 것"이나 "대기업이 쓰는 것"을 나열하는 게 아니다.
**이 서비스의 부하 형태에 맞고, 혼자 굴릴 수 있고, 고객 100명 시점에 월 200달러 안에 들어오는** 조합 하나를 근거와 함께 고르는 것이다.

결과물은 두 가지다.
1. `docs/stack-recommendation.md` — 조사 근거가 붙은 보고서 (양식: `references/report-template.md`)
2. 채팅 요약 — 추천 스택 한 줄, 3개 규모 시점의 월 비용, 가장 큰 비용 함정 하나

## 고정 전제 (매번 다시 묻지 말 것)

- 1인 개발, 부트스트랩. 개발·운영·고객응대를 한 사람이 한다
- 인프라 월 상한 200달러 (고객 100명 시점 기준, 엄격)
- 시장: 한국 먼저, 그다음 글로벌. 결제는 국내 토스페이먼츠 / 해외 MoR
- 내 시간의 값: 기본 3만원/시간. 사용자가 다른 값을 말하면 그걸 쓴다

**편의성은 감상이 아니라 시간이다.** 어떤 선택의 진짜 월 비용은 `현금 + (내 운영 시간 × 시급)`이다. 월 4달러 VPS가 매달 5시간을 먹으면 월 19달러 관리형보다 비싸다. 모든 비교는 이 합산값으로 한다.

운영 시간을 레이어별로 적을 때는 **그 레이어가 추가로 만드는 시간(한계 시간)만** 센다. 같은 박스에 올린 Postgres는 VPS의 패치·백업 시간과 대부분 겹치므로, VPS 3시간 + DB 1.5시간으로 적으면 실제보다 비싸 보인다. 이 이중계상 하나가 셀프호스트와 관리형의 승패를 뒤집을 수 있다.

## 판단 원칙 — 왜 이렇게 고르는가

**부품 수가 곧 장애 표면이다.** 혼자일 때 서비스 8개를 엮은 스택은 8곳에서 죽고, 8개 청구서가 오고, 8개 대시보드를 본다. 같은 일을 하면 부품이 적은 쪽이 이긴다. 2개 이상의 클라우드 계정, 쿠버네티스, 마이크로서비스, 멀티리전은 이 규모에서 후보에 넣지 않는다.

**무료 티어는 계약이 아니다.** Heroku(2022), Railway(2023), PlanetScale(2024)의 무료 티어는 사라졌고, Vercel Hobby는 상업 사용을 금지한다. 무료 티어를 0원으로 적지 말고, **다음 유료 티어 가격을 "실제 비용"으로 병기**한다. 무료로 시작해도 되지만 비용표는 유료 기준으로 짠다.

**예측 불가능한 비용이 큰 비용보다 위험하다.** 1인에게 월 30달러 정액은 견딜 수 있어도, 상한 없는 종량제에서 한 번 터지는 800달러 청구서는 사업을 끝낼 수 있다. 종량제 후보는 반드시 **지출 상한을 걸 수 있는지** 확인한다. AWS/GCP의 예산 알림은 상한이 아니라 알림이다.

**락인은 데이터 층에서만 따진다.** 호스팅은 Docker 이미지면 하루에 갈아탄다. 갈아타기 어려운 건 DB, 파일 스토리지, 인증(사용자 테이블)이다. 이 세 층은 표준(Postgres, S3 호환 API, OIDC/표준 세션)을 우선하고, 독자 API에 붙는 선택은 탈출 비용을 적는다.

**"전문가가 쓰는 것"의 기준은 우리 규모다.** 컨설턴트가 대기업에 권하는 것과 1인 창업자에게 권하는 것은 다르다. 증거로 인정하는 건 우리 규모(1~2인, 월 매출 1만 달러 이하)의 사례뿐이다. 스타트업 CTO의 "Vercel에서 Hetzner로 옮겼더니 월 500달러 줄었다" 같은 글은 증거이고, 넷플릭스 아키텍처 블로그는 증거가 아니다.

**한국 서비스는 한국 조건이 있다.** 리전(서울 유무, 도쿄·싱가포르 지연), 카카오·네이버 로그인 지원, 알림톡, 토스페이먼츠, .kr 도메인, Stripe 국내 사업자 미지원. 해외 서비스 조합에서 이 조건들이 빠지면 나중에 되돌아온다. `references/candidates.md`의 "한국" 항목을 확인한다.

**기억으로 가격을 쓰지 않는다.** 이 분야는 12개월 안에 가격표가 바뀐다. 후보의 가격·무료 티어 조건·리전은 반드시 웹 검색으로 현재 값을 확인하고, 보고서에 URL과 확인 날짜를 적는다. `references/candidates.md`의 숫자는 출발점이지 답이 아니다.

## 진행 방식: Phase 0에서 한 번 멈추고, 그다음은 쭉 간다

Phase 0(서비스 파악)이 틀리면 뒤의 조사가 전부 무의미하다. 그래서 프로필 확인 후 한 번 멈춘다. 사용자가 "그냥 쭉 해줘"라고 하면 멈추지 않는다.

### Phase 0 — 서비스 파악 → 워크로드 프로필

**레포가 있으면 먼저 읽는다.** 사용자에게 묻기 전에 코드가 답하는 것을 다 뽑아낸다.

| 볼 것 | 알 수 있는 것 |
|---|---|
| `package.json` / `requirements.txt` / `go.mod` | 런타임, 프레임워크 (Next.js면 SSR·ISR·이미지 최적화 의존 여부까지) |
| `Dockerfile`, `docker-compose.yml` | 컨테이너 준비 여부, 부속 서비스(Redis, 워커) |
| `prisma/schema.*`, `migrations/`, ORM 설정 | DB 종류, 데이터 크기 추정, 관계형인지 |
| `vercel.json`, `fly.toml`, `wrangler.toml`, `.github/workflows` | 현재 배포 방식과 그 흔적 |
| `.env.example` — **변수 이름만** 본다, 값은 절대 출력하지 않는다 | 외부 서비스 의존 (S3, SMTP, 결제 키, LLM API) |
| 업로드 핸들러, `sharp`/`ffmpeg`/`puppeteer`, 웹소켓, 큐, 크론 | 파일·미디어 부하, 실시간, 장시간 작업 |

레포가 비어 있거나 부족하면 `references/interview.md`의 질문을 쓴다. **대화에 이미 답이 있는 건 다시 묻지 않는다.** 한 번에 다 묻지 말고, 프로필을 채우는 데 꼭 필요한 것만 묻는다.

**출력 — 워크로드 프로필 카드** (이 형태로 보여주고 멈춘다):

```
서비스: (한 줄)
컴퓨트 형태: 요청-응답 / 장시간 작업(PDF·영상·LLM) / 실시간(웹소켓) / 혼합
데이터 형태: 관계형 / 문서 / 파일·미디어 중심 (예상 용량, 월 다운로드량)
트래픽: 거의 0에서 시작 / 예측 가능한 B2B 업무시간 / 스파이크(바이럴·마케팅)
규모 시점: 출시 직후 → 고객 100명 → 고객 1,000명 (각 시점의 MAU·요청·저장량 추정)
지역·규제: 한국 사용자 비율, 개인정보 국외 이전 여부, 특수 요건
정지 내성: 3일 멈추면 고객에게 무슨 일이 생기는가 → 관리형 필요 / 셀프호스트 허용
내 운영 허용 시간: 월 N시간
LLM 사용: 있음(모델·호출당 토큰 추정) / 없음
```

**비용이 새는 지점 1~2개를 여기서 지목한다.** 대부분의 스택에서 청구서의 80%는 한두 항목이다 — 파일 다운로드(egress), 이미지 변환, 장시간 실행, DB 연결 수, LLM 토큰, 알림톡·SMS 발송량. 이걸 먼저 찾아야 뒤의 후보 선택이 그 항목 중심으로 돌아간다. `references/cost-traps.md`의 목록과 대조한다.

**지목한 항목이 인프라가 아니면, 플랫폼 질문은 틀린 질문이다.** 건당 원가가 붙는 항목(알림톡·SMS, LLM 토큰, 외부 API 호출, 결제 수수료)은 호스팅·DB·스토리지를 전부 합친 것보다 큰 경우가 흔하다. 그럴 때 "Vercel이냐 VPS냐"를 오래 따지는 것은 청구서의 10%를 놓고 다투는 것이다. 이 경우 **먼저 그 항목을 정면으로 다루고**, 인프라 추천은 그다음에 짧게 낸다. 사용자가 "호스팅 뭐 쓸까"로 물었더라도 답이 "발송 정책부터 정하십시오"가 되는 것은 정상이며, 그것이 이 스킬이 해야 할 일이다.

프로필 아래에 "이 프로필이 맞나요? 틀린 곳을 고쳐주시면 조사를 시작합니다"로 끝내고 **멈춘다.**

### Phase 1 — 현업 조사 (웹 검색 필수)

`references/research-playbook.md`를 읽고 그대로 한다. 핵심만 요약하면:

1. 프로필에서 지목한 **비용 유출 지점**을 가장 잘 막는 후보부터 찾는다. 예: egress가 문제면 R2·B2 같은 egress 무료 스토리지가 중심이 되고, 호스팅은 그 다음이다.
2. 각 레이어(호스팅, DB, 스토리지, 인증, 결제, 이메일·알림, 백그라운드 작업, 모니터링, CI/DNS)마다 후보 2~3개. `references/candidates.md`에서 출발하되, **검색으로 현재 가격·무료 티어 조건·리전을 재확인**한다.
3. "실제로 쓰는 사람"의 증거를 찾는다: 청구서 공유 글, 이전(migration) 후기, 가격 인상 반응 스레드, 최근 12개월 서비스 종료·정책 변경. 한국어 커뮤니티(GeekNews, 디스콰이엇, velog, 커리어리)와 영어(HN, r/selfhosted, r/webdev, Indie Hackers) 둘 다 본다.
4. 후보마다 3가지를 반드시 기록: **무료 티어 상업 사용 가능 여부, 최근 12개월 가격·정책 변경, 한국에서의 지연(리전)**.

LLM 레이어가 있으면 토큰 단가·캐싱·배치 할인은 반드시 공식 가격 페이지로 확인한다. `claude-api` 스킬이 있으면 그것을 참조한다.

### Phase 2 — 레이어별 비교와 비용 시뮬레이션

레이어마다 아래 표를 만든다. 편의성 점수는 `references/report-template.md`의 5항목(배포 마찰, 월 운영 시간, 한밤중 장애 시 내 개입 필요, 로컬 개발 동일성, 탈출 비용)으로 채점한다.

| 후보 | 출시 직후 | 고객 100명 | 고객 1,000명 | 월 운영 시간 | 편의성 | 상한 설정 | 한국 리전 | 비고·함정 |

**레이어 비교와 함께 항목별 비중 표를 반드시 만든다.** 고객 100명 시점의 월 현금 비용을 항목별로 쪼개고 비중(%)을 적는다. 이 표가 없으면 "인프라를 열심히 최적화했는데 청구서의 10%였다"는 실수를 못 잡는다. 인프라 합계가 전체의 30% 미만이면 그 사실을 추천의 첫 문장으로 올린다.

**비용 계산은 손으로 하지 말고 `scripts/estimate_cost.py`를 쓴다.** 프로필의 사용량과 조사한 단가를 JSON에 넣으면 3개 규모 시점의 현금 비용 + 시간 비용 합산표가 나온다. `assets/pricing.example.json`을 복사해 조사한 숫자로 덮어쓴 뒤 실행한다. 숫자를 바꾸면 표가 즉시 다시 나오므로, 사용자가 "다운로드가 2배면?" 하고 물을 때 바로 답할 수 있다.

```bash
python scripts/estimate_cost.py --profile <profile.json> --pricing <pricing.json> \
  --stack "hetzner-cx22,coolify-postgres,cloudflare-r2,resend-free" --hourly-rate 30000
```

### Phase 3 — 추천

**정확히 하나의 주 스택과 하나의 대안**을 낸다. 대안은 주 스택과 철학이 달라야 한다 (관리형 ↔ 셀프호스트, 정액 ↔ 종량제). 셋 이상 나열하면 결정을 사용자에게 떠넘기는 것이다.

각 스택에 반드시 포함할 것:
- 레이어별 선택과 **한 줄 이유** (조사 근거 URL 붙임)
- 3개 규모 시점의 월 총액 = 현금 + 시간 비용. 200달러 상한과 비교
- **이 추천이 틀리는 조건** — 예: "월 다운로드가 5TB를 넘으면 호스팅을 X로 바꿔야 한다". 이게 없으면 추천이 아니라 취향이다
- 가장 큰 비용 함정 하나와 그 방어책 (상한 설정, 알림, 캐싱)
- 갈아타기 경로 — 규모가 커졌을 때 어느 층을 어디로 옮기는가
- **사지 말아야 할 것** — 지금 규모에서 돈 낭비인 것들 (유료 모니터링, 멀티리전, 전용 DB 인스턴스 등)
- 첫 주에 할 일 5개 이내

보고서를 `docs/stack-recommendation.md`에 저장하고 채팅에는 요약만 쓴다. 채팅 요약은 표 하나(스택 × 3시점 비용)와 함정 하나, 그리고 "이 다음에 뭘 할까요"로 끝난다.

## 자주 하는 실수

- **프로필 없이 후보부터 나열한다.** 서비스가 뭔지 모르면서 "Vercel vs Cloudflare"를 논하는 것. Phase 0을 건너뛰지 않는다.
- **무료 티어 합산으로 "월 0원" 스택을 만든다.** 6개월 뒤 청구서와 다르다. 유료 기준 병기.
- **셀프호스트를 운영 시간 0으로 계산한다.** 백업 확인, 보안 패치, 디스크 꽉 참, 한밤중 재시작 — 월 2~5시간은 잡는다. 정지 내성이 낮은 서비스면 관리형이 맞다.
- **대기업 사례를 근거로 쓴다.** 규모가 다르면 정답도 다르다.
- **한국 조건을 마지막에 붙인다.** 카카오 로그인 미지원 인증, 서울 리전 없는 DB, 국내 사업자 못 쓰는 결제(Stripe)는 처음부터 후보에서 뺀다.
- **가격을 기억으로 쓴다.** 검색 안 한 숫자는 보고서에 넣지 않는다.
- **후보를 5개씩 나열하고 끝낸다.** 하나를 고르고 틀리는 조건을 적는다.
