# 빌드 명령 — Claude Code에 붙여넣기

각 단계를 **따로** 붙여넣는다. 한 번에 다 주면 검증 없이 끝까지 달린다.

명령 3(서명)과 명령 6b(보안 점검) 전에는 `05-SECURITY.md`를 먼저 읽히고 시작한다.

## 명령 0 — Day 0 미끼 도구 (반나절)

```
안전운임 확인서 생성기를 한 페이지짜리로 만들어줘.

목적: 이 도구가 실제로 쓰이는지 관찰하는 것. 제품이 아니라 실험이다.

요구사항
- Next.js 단일 페이지. 로그인·DB 없음
- 확인서 3종 선택: 대기시간 / 험로·오지 / 세척·손상교체
- 각 종류별 입력 폼
- 대기시간은 도착·상차·하차 시각을 **기록만** 한다. 초과 시간이나 청구 가능 여부를
  계산하지 마라 — 그 기준은 아직 원문 대조가 안 끝났다
- 손가락 서명 캡처 (canvas)
- "PDF 내려받기" 버튼 → 한글 폰트 임베드된 PDF 생성
- 모바일 우선. 한 손으로 쓸 수 있어야 함

측정
- 생성 횟수, 확인서 종류별 분포, 재방문 여부를 익명 카운터로 기록
- 개인정보는 저장하지 않는다. 입력값은 브라우저 안에서만 처리

하지 말 것
- 계정, DB, 결제, 운임 금액 계산
- 확정되지 않은 요율·할증·기준시간 숫자를 넣는 것. 어떤 형태로도
- 개인정보를 서버로 보내는 것 (입력값은 브라우저 안에서만 처리)

배포는 Vercel 무료 티어 기준으로 잡아줘.
```

## 명령 1 — 규칙 확정 (Day 1~2)

**주의: 이 단계는 코드가 아니라 문서 작업이다. AI에게 숫자를 만들게 하지 말 것.**

```
02-RULES-v2026.md를 읽어줘.

내가 국토교통부 고시 원문과 운영지침을 첨부할 테니, 문서의 각 [ ] 항목을
원문과 대조해서 확정/불일치/원문에 없음 셋 중 하나로 표시해줘.

규칙
- 원문에서 근거 문장을 찾지 못한 항목은 절대 "확정"으로 표시하지 마라
- 추정하거나 일반 상식으로 채우지 마라. "원문에서 못 찾음"이 정답이다
- 원문과 초안이 다르면 원문을 따르고, 차이를 따로 목록으로 정리해줘

출력: 대조가 끝난 02-RULES-v2026.md 수정본 + 불일치 목록
```

## 명령 3 — 증빙 요청과 서명 (Day 5~7)

```
화면 2를 만들어줘.

요청 쪽 (운송사, 로그인 상태)
- 운송 건에서 증빙 종류 선택 → 토큰 링크 생성 (CSPRNG 32바이트, DB에는 해시만 저장, 만료 7일)
- 링크 복사 / SMS 발송
- 상태 표시: 요청됨 / 서명됨 / 만료

서명 쪽 (로그인 없음, 토큰 접근)
- 모바일 우선, 한 화면
- WAIT: 도착·상차·하차 시각 입력. 기산 기준이 02-RULES에서 확정됐을 때만 초과 시간을 표시하고, 아니면 '미지원'으로 둔다
- ROUGH_ROAD / WASH_SWAP: 체크 + 사진 첨부
- 손가락 서명 → 저장
- 저장 시 signer_ip, signer_user_agent 기록
- 만료된 토큰은 "만료됨" 안내만. 재발송 방법 표시

절대 지킬 것 (05-SECURITY.md의 '위협 1 — 토큰' 절을 먼저 읽어라)
- 서명자에게 회원가입·로그인을 요구하지 않는다. 어떤 이유로도
- 토큰: CSPRNG 32바이트, DB에는 해시로 저장, 상수 시간 비교, 만료 7일
- 토큰 1개 = 증빙 1건. 운송 건 전체나 회사에 접근시키지 않는다
- 서명 전 화면에 띄울 정보는 최소한으로 (운송 건 번호, 날짜, 품목, 요청 회사명)
- 없는 토큰과 만료된 토큰의 응답을 구분할 수 없게. 토큰 조회에 IP 속도 제한
- 모든 ID는 UUID. 자동증가 정수 금지

끝나면
- 계정 2개를 만들어 남의 ID·토큰을 실제로 넣어보고 결과를 보고해줘
```

## 명령 4 — PDF와 알림 (Day 8~9)

```
서명 완료 시 PDF를 생성하고 요청자에게 알려줘.

- 서버에서 HTML → PDF 렌더. 한글 폰트 임베드 필수 (안 하면 깨진다)
- PDF에 들어갈 것: 운송 건 정보, 증빙 종류별 입력값, 서명 이미지,
  서명 시각, calc_version
- 생성된 PDF는 스토리지에 저장하고 evidence.pdf_path에 기록
- 요청자에게 알림 (이메일 또는 앱 내 알림. SMS는 비용 때문에 선택)

확인
- 한글이 깨지지 않는지 실제 PDF를 열어 확인한 뒤 보고해줘
- 서식에 필수 항목이 빠지지 않았는지 02-RULES의 서식 절과 대조해줘
```

## 명령 4b — 개인정보 처리 (Day 9, 짧게)

```
이 서비스는 화주 담당자·차주의 이름, 연락처, 서명 이미지, 접속 IP를 저장한다.
개인정보를 다루는 서비스이므로 최소한의 장치를 넣어줘.

- 서명 화면에 수집 항목·목적·보관 기간을 한 줄로 고지하고 동의 받기
- 개인정보처리방침 페이지 (수집 항목, 목적, 보관 기간, 파기, 문의처)
- 보관 기간을 설정 가능하게 하고 기본값을 정해줘.
  분쟁 대비라는 목적상 몇 년이 적절한지 근거와 함께 제안해줘
- 기간 경과 데이터 파기 배치 (지금은 스크립트만. 자동 실행은 나중)
- 서명 이미지·첨부 사진에 직접 URL로 접근할 수 없게 (서명된 URL 또는 권한 검사)

법률 자문이 아니라 기술적 최소 장치다. 실제 문구는 내가 검토한다.
```

## 명령 6b — 보안 점검 (Day 12, 원가 점검과 같은 날)

```
05-SECURITY.md를 읽고 전 항목을 코드에 대조해줘.

방식
- 항목마다 적용됨 / 안 됨 / 해당 없음으로 판정
- "안 됨"은 고치는 코드까지 같이 내줘
- 판정 근거로 실제 코드 위치(파일:줄)를 적어줘. 추측으로 적용됨이라고 하지 마라

특히 실제로 실행해서 확인할 것
1. 계정 2개로 남의 company_id 데이터에 접근 시도
2. 토큰 문자열을 임의로 바꿔 다른 증빙에 접근 시도
3. 없는 토큰 / 만료된 토큰의 응답이 구분되는지
4. 서명 이미지·첨부 파일을 URL만으로 열 수 있는지
5. 업로드에 SVG와 위장 확장자 파일을 넣어보기
6. 내려받은 CSV의 셀이 = 로 시작할 때 어떻게 되는지
7. .env가 git에 올라가 있는지, 로그에 토큰·연락처가 남는지

마지막에 "가장 위험한 구멍 3개"를 심각도 순으로 알려줘.
```
